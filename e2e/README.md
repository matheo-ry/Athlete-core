# e2e

Tests de flujos completos con Playwright: abren la app en un navegador de verdad (Chromium) y la usan como un usuario.

- **Cómo se ejecutan:** `npm run test:e2e`. La primera vez en un ordenador hay que descargar el navegador: `npx playwright install chromium`.
- **Necesitan Supabase local** (desde el PR 1.3): `npm run db:start`, `npm run db:reset` y `.env.local` con los valores de `npx supabase status`. Entran con los usuarios inventados de `supabase/seed.sql` (`helpers.ts`).
- **Qué va aquí:** un test por flujo crítico (login, unirse con código, asignar rutina, registrar entreno) según AGENTS.md §6. `auth.spec.ts` prueba entrar y cerrar sesión; `email-codes.spec.ts`, recuperar la contraseña y entrar con un código por email; `signup.spec.ts`, el registro; `join.spec.ts`, la primera pantalla y unirse con código; `clients.spec.ts`, la lista de clientes y el código de invitación; `create-business.spec.ts`, de "¿Eres coach?" a tener el negocio; `archive.spec.ts`, dar de baja y reactivar (cada test crea su propio negocio con `createTestBusiness`); `profile.spec.ts`, el perfil y cambiar la contraseña; `spaces.spec.ts`, el selector de espacio y "Mis espacios"; `brand.spec.ts`, la marca del coach (con su propio negocio, para no cambiar los colores del seed); `logo.spec.ts`, el logo contra el Storage local (también que Storage rechaza un SVG, más de 2 MB o la carpeta de otro negocio aunque no se pase por la app); `smoke.spec.ts`, que la app arranca sin errores.
- **Idioma:** al entrar, la app se pone en el idioma de la cuenta (D-058). Los usuarios del seed que usan los tests tienen la cuenta en inglés. Las cuentas creadas con `createConfirmedUser(…, 'es')` ven la app en español en cuanto entran. Con sesión, cambiar el idioma cambia la cuenta: un test que lo haga usa una cuenta propia, nunca una del seed (los tests van en paralelo y otro la vería cambiada).
- **Cerrar sesión** está en Ajustes (coach) o en Perfil (cliente), no en la cabecera: usa `signOut(page)` de `helpers.ts`.
- **Varios espacios:** `coach.iron@example.com` es dueña de Iron Lab y clienta de Norte Strength. Al entrar en un navegador nuevo ve el selector: usa `chooseSpace(page, 'Iron Lab')`.
- **Cuentas de prueba:** los tests que cambian una cuenta (por ejemplo, su contraseña) crean la suya con `supabase-helpers.ts` (`createConfirmedUser`) y leen los códigos de la bandeja local (`latestCode`). Así no tocan los usuarios del seed. Las cuentas `e2e-…@example.com` desaparecen con `npm run db:reset`. Quien se une a Norte Strength en un test queda dado de baja al terminar (`archiveFromNorte`), para que su plan no se llene si los tests se repiten.
- **"Demasiados intentos":** en local todas las peticiones llegan desde la misma dirección IP. Si repites los tests muchas veces seguidas, espera 10 minutos o ejecuta `npm run db:reset` (D-065). Por eso los códigos equivocados se prueban con sesión, que cuenta por usuario.
- **Qué no va aquí:** tests de lógica o de un componente suelto. Esos van con Vitest, junto al archivo que prueban.
- **En el CI** (desde el PR 3.1b): el trabajo "Tests de flujos completos" de `.github/workflows/ci.yml` arranca Supabase local, escribe `.env.local` con sus valores y `VITE_ALLOW_WEB_WORKOUTS=true`, y ejecuta `npm run test:e2e`. Si falla, el informe se descarga desde la ejecución ("Artifacts"). No forman parte de `npm run check`.
- **Entrenos en el navegador:** los tests de entreno necesitan `VITE_ALLOW_WEB_WORKOUTS=true` en `.env.local` (D-116).
- Solo datos inventados.
